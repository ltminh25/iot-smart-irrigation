1. Bối cảnh & mục tiêu

Xây dựng hệ thống IoT giám sát – điều khiển chăm sóc cây tự động: 4 loại cảm biến (ánh sáng, độ ẩm đất, nhiệt độ/độ ẩm không khí, mưa), 2 cơ cấu chấp hành (mái che servo, bơm relay), giao tiếp qua MQTT, backend Python xử lý nghiệp vụ + REST API + realtime, frontend React làm dashboard quản trị. Yêu cầu bắt buộc: auth JWT, RBAC 3 vai trò, quản lý vòng đời thiết bị, rule engine cảnh báo/tự động hoá, lịch sử telemetry, audit log.

AI khi generate code phải tuân thủ đúng schema, endpoint, luật nghiệp vụ mô tả trong tài liệu này — không tự ý đổi tên field, đổi role, hay bỏ bớt kiểm tra quyền.

2. Tech stack bắt buộc

Backend (Python):

  • Framework: FastAPI (async, tự sinh OpenAPI docs)
  • ORM: SQLAlchemy 2.x (async) + Alembic cho migration
  • DB: PostgreSQL
  • MQTT client: paho-mqtt hoặc gmqtt (async), chạy như background service trong FastAPI (lifespan event)
  • Realtime tới frontend: WebSocket native của FastAPI (fastapi.WebSocket), không dùng Socket.IO ở backend để tránh phụ thuộc thêm — nếu cần Socket.IO thì dùng python-socketio ASGI app mount vào FastAPI
  • Auth: JWT (python-jose hoặc pyjwt) access token + refresh token, hash password bằng passlib[bcrypt]
  • Validation: Pydantic v2 cho toàn bộ request/response schema
  • Background jobs (heartbeat timeout check, retry lệnh): APScheduler hoặc asyncio task chạy nền
  • Test: pytest + httpx.AsyncClient
  • Container: Docker + docker-compose (backend, postgres, mosquitto)

Frontend (React):

  • React 18 + TypeScript, Vite làm build tool
  • Routing: react-router-dom
  • State/data fetching: TanStack Query (React Query) + axios
  • Realtime: native WebSocket API hoặc socket.io-client (khớp với lựa chọn backend)
  • Chart: Recharts
  • UI kit: chọn 1 trong (MUI / Ant Design / Tailwind + shadcn/ui) — AI có thể chọn Ant Design vì có sẵn Table/Form/RBAC menu phù hợp dashboard quản trị
  • Auth state: Context API hoặc Zustand, lưu access token trong memory, refresh token trong httpOnly cookie (khuyến nghị) hoặc localStorage nếu đơn giản hoá cho đồ án

4. Database schema

CREATE TABLE roles (
  id SERIAL PRIMARY KEY,
  name VARCHAR(20) UNIQUE NOT NULL  -- admin | owner | viewer
);

CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username VARCHAR(50) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  email VARCHAR(120) UNIQUE NOT NULL,
  role_id INT REFERENCES roles(id) NOT NULL,
  status VARCHAR(20) DEFAULT 'active', -- active | locked
  failed_login_count INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE devices (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_uid VARCHAR(100) UNIQUE NOT NULL,
  name VARCHAR(100) NOT NULL,
  owner_id UUID REFERENCES users(id) NOT NULL,
  location VARCHAR(150),
  status VARCHAR(20) DEFAULT 'registered', -- registered|provisioned|active|offline|fault|maintenance|decommissioned
  firmware_version VARCHAR(20),
  api_key VARCHAR(255) UNIQUE NOT NULL,
  last_heartbeat_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE device_lifecycle_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_id UUID REFERENCES devices(id) NOT NULL,
  from_state VARCHAR(20),
  to_state VARCHAR(20) NOT NULL,
  changed_by UUID REFERENCES users(id),
  timestamp TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE telemetry (
  id BIGSERIAL PRIMARY KEY,
  device_id UUID REFERENCES devices(id) NOT NULL,
  sensor_type VARCHAR(20) NOT NULL, -- light|soil|air_temp|air_humidity|rain|waterlevel
  value NUMERIC NOT NULL,
  unit VARCHAR(10),
  timestamp TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_telemetry_device_time ON telemetry(device_id, timestamp DESC);

CREATE TABLE commands (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  command_id VARCHAR(50) UNIQUE NOT NULL,
  device_id UUID REFERENCES devices(id) NOT NULL,
  action VARCHAR(30) NOT NULL, -- pump_on|pump_off|curtain_open|curtain_close
  payload JSONB,
  issued_by UUID REFERENCES users(id),
  status VARCHAR(20) DEFAULT 'pending', -- pending|executed|failed
  issued_at TIMESTAMPTZ DEFAULT now(),
  executed_at TIMESTAMPTZ
);

CREATE TABLE alert_rules (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sensor_type VARCHAR(20),
  condition VARCHAR(20), -- gt|lt|eq|...
  threshold NUMERIC,
  action VARCHAR(50),    -- ví dụ 'trigger_alert', 'auto_pump_on'
  enabled BOOLEAN DEFAULT true
);

CREATE TABLE alerts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_id UUID REFERENCES devices(id) NOT NULL,
  rule_id UUID REFERENCES alert_rules(id),
  message VARCHAR(255) NOT NULL,
  severity VARCHAR(20) DEFAULT 'warning', -- info|warning|critical
  status VARCHAR(20) DEFAULT 'open', -- open|acknowledged|resolved
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE audit_log (
  id BIGSERIAL PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  action VARCHAR(100) NOT NULL,
  target VARCHAR(100),
  timestamp TIMESTAMPTZ DEFAULT now()
);

5. RBAC – ma trận vai trò & quyền

Chức năng Admin Owner Viewer
Quản lý user ✔ ✘ ✘
Đăng ký thiết bị mới ✔ ✔ ✘
Xem dữ liệu thiết bị của mình ✔ ✔ ✔
Xem dữ liệu thiết bị của người khác ✔ ✘ ✘
Gửi lệnh điều khiển ✔ ✔ ✘
Cấu hình ngưỡng cảnh báo ✔ ✔ (thiết bị của mình) ✘
Khóa/decommission thiết bị ✔ ✔ (thiết bị của mình) ✘
Xem audit log ✔ ✘ ✘

Yêu cầu implement bắt buộc:

  • Middleware/dependency require_role(*roles) áp dụng trên từng endpoint.
  • Với owner: mọi endpoint liên quan device phải kiểm tra thêm device.owner_id == current_user.id (trừ admin).
  • Không được chỉ ẩn nút trên UI — mọi kiểm tra quyền phải nằm ở backend, UI chỉ ẩn/hiện để trải nghiệm tốt hơn.

6. Authentication

  • POST /api/auth/register — tạo user role mặc định owner (admin tạo qua /api/users nếu cần role khác).
  • POST /api/auth/login — verify bcrypt hash, trả access_token (hết hạn ~15 phút) + refresh_token (hết hạn dài hơn, ví dụ 7 ngày).
  • POST /api/auth/refresh — cấp access token mới từ refresh token hợp lệ.
  • PUT /api/users/me/password — đổi mật khẩu, yêu cầu mật khẩu cũ.
  • Giới hạn đăng nhập sai: sau N lần sai (ví dụ 5), khóa tạm tài khoản (status = locked), ghi audit log.
  • JWT payload tối thiểu: {sub: user_id, role: role_name, exp}.

7. Vòng đời thiết bị (state machine)

Registered → Provisioned → Active → Offline/Fault → Maintenance → Decommissioned
Trạng thái Sự kiện chuyển
Registered Owner/Admin tạo mới qua POST /api/devices (sinh device_uid + api_key)
Provisioned Đánh dấu khi api_key đã được nạp vào firmware (thao tác thủ công hoặc endpoint riêng)
Active Backend nhận heartbeat đầu tiên qua MQTT
Offline/Fault Không nhận heartbeat > 30s (job nền check định kỳ) hoặc thiết bị báo lỗi
Maintenance Owner/Admin khóa tạm qua PUT /api/devices/{id}/status
Decommissioned Owner/Admin thao tác thủ công → vô hiệu hóa api_key, mọi bản tin MQTT từ device này bị reject

Mọi lần chuyển trạng thái phải ghi vào device_lifecycle_log.

8. MQTT — topic, payload, độ tin cậy

Topic:

plant/{deviceId}/telemetry/light
plant/{deviceId}/telemetry/soil
plant/{deviceId}/telemetry/air
plant/{deviceId}/telemetry/rain
plant/{deviceId}/telemetry/waterlevel
plant/{deviceId}/status
plant/{deviceId}/cmd/curtain
plant/{deviceId}/cmd/pump
plant/{deviceId}/ack

Payload telemetry:

{"deviceId":"esp32-plant-001","timestamp":"2026-09-06T10:15:30Z","type":"soil","value":28.5,"unit":"%"}

Payload lệnh (backend → thiết bị):

{"commandId":"cmd-000123","deviceId":"esp32-plant-001","action":"pump_on","duration":5000,"issuedBy":"user-001","timestamp":"2026-09-06T10:16:00Z"}

Payload ack (thiết bị → backend):

{"commandId":"cmd-000123","deviceId":"esp32-plant-001","status":"executed","timestamp":"2026-09-06T10:16:02Z"}

Yêu cầu implement:

  • QoS = 1 cho telemetry và cmd; xử lý trùng lặp bằng commandId.
  • Timeout 5s không nhận ack → gửi lại, tối đa 3 lần → đánh dấu failed.
  • Heartbeat mỗi 15s từ thiết bị; job nền check mỗi ~10s để phát hiện thiết bị quá 30s không heartbeat → set offline, sinh alert.
  • Dùng MQTT Last Will and Testament để broker tự publish trạng thái offline khi mất kết nối đột ngột.
  • MQTT subscriber validate: device tồn tại + đang ở trạng thái cho phép publish (không phải decommissioned), giá trị nằm trong khoảng hợp lệ (độ ẩm 0–100%, nhiệt độ -10–60°C...) — reject và log nếu sai.
  • Backend không expose endpoint HTTP public cho thiết bị publish trực tiếp — chỉ qua MQTT.

9. Rule engine (đánh giá sau mỗi telemetry mới)

Điều kiện Hành động
Ánh sáng > 10000 lux Publish lệnh đóng mái che + log
Mưa = true Publish lệnh mở mái che, huỷ lệnh tưới đang chờ
Độ ẩm đất < 30% AND nhiệt độ < 35°C AND không mưa AND mực nước đủ Publish lệnh bật bơm 5s
Độ ẩm đất < 30% AND nhiệt độ ≥ 35°C Sinh alert "chờ tưới do nhiệt độ cao", không tưới
Mực nước = thấp Sinh alert "cần châm nước", chặn lệnh bật bơm
Nhiệt độ > 30°C AND độ ẩm KK > 80% kéo dài > 30 phút Sinh alert "nguy cơ nấm mốc"
Không heartbeat > 30s Set device = offline, sinh alert

Alert lưu bảng alerts với status=open; user (owner của device hoặc admin) có quyền acknowledge / resolve qua API.

11. Bảo mật — checklist bắt buộc

  • Hash password bằng bcrypt/argon2, không log/lưu plaintext.
  • JWT access token thời hạn ngắn + refresh token riêng.
  • Middleware kiểm tra role + ownership trên mọi endpoint nhạy cảm (không chỉ ẩn UI).
  • Mỗi thiết bị có device_uid + api_key/MQTT credential riêng biệt.
  • .env chứa toàn bộ secret, có .env.example không chứa giá trị thật, .gitignore loại .env.
  • Validate input chặt (Pydantic) cho mọi API và mọi payload MQTT.
  • Decommission thiết bị → vô hiệu hoá api_key ngay, broker/backend reject mọi bản tin sau đó.
  • Audit log cho: đăng nhập, đổi quyền, khoá/decommission thiết bị, gửi lệnh điều khiển.
  • HTTPS cho API, mqtts:// (TLS) cho MQTT nếu broker hỗ trợ.
  • Giới hạn số lần đăng nhập sai để chống brute-force.

2 kịch bản bảo mật tối thiểu cần AI viết test cho:

  1. Viewer gửi lệnh điều khiển → backend trả 403 Forbidden.
  2. Thiết bị đã decommissioned publish dữ liệu → bị từ chối, không ghi DB.

9. Audit log cho các hành động nhạy cảm (login, đổi quyền, khoá/decommission device, gửi lệnh).

Frontend: màn hình Login, Dashboard realtime (4 chỉ số + trạng thái + alert mở), Chi tiết thiết bị (biểu đồ lịch sử + nút điều khiển thủ công), Quản lý thiết bị, Quản lý user (chỉ admin), Alerts (list + acknowledge/resolve), Lịch sử lệnh điều khiển. Menu/UI ẩn hiện theo role nhưng luôn dựa vào quyền thật trả về từ backend.
11. Viết test: unit test rule engine, integration test API (bắt buộc test case viewer bị 403 khi gửi lệnh, và device đã decommission bị reject khi publish).
12. Cung cấp Dockerfile cho backend & frontend, docker-compose gồm backend + frontend + postgres + mosquitto, .env.example đầy đủ biến môi trường.

Hãy generate theo thứ tự: (1) DB models + migration → (2) auth + RBAC middleware → (3) device CRUD + state machine → (4) MQTT service + rule engine → (5) command service (gửi lệnh, retry) → (6) WebSocket broadcast → (7) alert/audit API → (8) frontend auth & routing theo role → (9) dashboard realtime → (10) các màn hình quản lý còn lại → (11) test.
